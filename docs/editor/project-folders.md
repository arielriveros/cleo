# Project folders

In the desktop app every project is a folder on disk. The folder is the project: you can put it under git,
copy it to another machine, or open it from both the installed app and a development build. Cleo keeps its own
copy of the project in its internal storage only as a cache, so opening a project is fast; the cache can be
thrown away at any time, and the folder is read again.

The web editor keeps projects in the browser's storage, as before.

## Choosing a location

Creating a project, installing an example or importing a `.zip` asks where the project's folder goes. By
default that is a folder named after the project inside `Documents/Cleo Projects`; **Browse…** picks another
place. A folder that already holds a project is refused (open it with **Open Folder…** instead); any other
folder, an empty git repository for example, is fine.

Two options come with a new folder:

- **Create a git repository** runs `git init` in it (ticked when git is installed).
- **Install the script tools** runs `npm install` in it, in the background, for type-checking and tests
  (ticked when npm is installed).

## What is in the folder

| Path | What it is |
|---|---|
| `project.cleo` | The project file: its name and main scene. Double-click it to open the project in Cleo. |
| `Assets/` | Everything in the [Assets](assets.md) panel, in the same folders: scenes, scripts (`.ts`), materials, models, textures and their images, sounds and their audio files. |
| `*.meta` | Every asset file has one beside it, holding the asset's identity. See [Metadata](#metadata). |
| `Blobs/` | Mesh, animation, terrain and tilemap data, in files named by their content. Never edited by hand. |
| `Baked/` | Baked GI and water. |
| `Derived/` | Generated data that ships but has no place in the Assets panel (a model's LOD textures). |
| `ProjectSettings/` | Project settings and input bindings. |
| `tests/` | Script unit tests (see [Scripts](#scripts-and-npm)). |
| `package.json`, `tsconfig.json`, `.vscode/` | Tooling for working on the scripts outside Cleo. |
| `.cleo/`, `node_modules/` | Regenerated by Cleo and npm. Not part of the project; ignored by git. |

The Assets panel mirrors `Assets/`: creating, renaming, moving or deleting an asset in Cleo does the same to
its file (deleted files go to the system trash). A file name that a file system would refuse is written with
`%` escapes (`a:b.mat` becomes `a%3Ab.mat`).

## Metadata

An asset's `.meta` file holds its id. Everything that uses an asset (a material slot, a placed model, a
foliage rule) refers to that id, never to the file name, so:

- **moving or renaming a file together with its `.meta`** keeps every reference to it — in Cleo, in a file
  manager or with `git mv`;
- **copying a file together with its `.meta`** makes a new asset: the copy is given a new id the next time the
  project opens;
- **a file without a `.meta`** (a picture or a sound dropped into `Assets/`) becomes a new asset, and Cleo writes
  its `.meta`. A dropped image also gets a texture beside it, a dropped sound a sound sample.

A meta never changes when the asset is edited, so a commit shows the files that really changed. Rendered
thumbnails are not stored in the folder; Cleo draws them again.

## Changes outside Cleo

Cleo watches the folder while the project is open.

- **A script edited in another program** (VS Code) is taken in at once, its open tab included.
- **Anything else** — a `git pull`, a branch checkout, a file added, moved or deleted outside Cleo — shows
  **Changed on disk** in the menu bar. **Reload from disk** reads the folder again; the project stays open.
- **A file Cleo cannot read** (one left with git merge-conflict markers, or a Git LFS pointer whose content was
  never downloaded) is listed under **Unreadable files**. Cleo keeps its own copy and never overwrites the file
  until it reads again.
- **A file changed on disk while Cleo was about to write it** is not overwritten: it is listed as a conflict,
  and **Reload from disk** shows the disk's version.
- **Many deletions at once**: when writing the project would delete more than a few files, Cleo asks first.

Only one Cleo writes a folder at a time: a project already open in another Cleo window is refused.

## Git

`.gitattributes` keeps text files (scenes, assets, metas, scripts) with LF line endings and sends binary files —
images, audio, `Blobs/`, `Baked/`, `Derived/` — through [Git LFS](https://git-lfs.com). Run `git lfs install`
once per machine before committing or cloning. A clone without LFS shows its binary files as **Unreadable
files**: run `git lfs pull`.

After a `git pull` or a checkout with the project open, use **Reload from disk**.

## Scripts and npm

The folder is also a TypeScript project for the scripts under `Assets/`. Its `package.json` has:

| Command | Does |
|---|---|
| `npm install` | Once: installs TypeScript and Vitest. |
| `npm run typecheck` | Checks every script against the engine's types. |
| `npm run watch` | The same, continuously. |
| `npm run play` | Plays the game in Cleo (Play in window), opening the project first if needed. |
| `npm run debug` | The same, with VS Code's debugger: press **F5** (*Debug Cleo game*) in VS Code. |
| `npm test` | Runs the script tests in `tests/`. |

See [Debugging](debugging.md#debugging-in-vs-code).

### Script tests

`npm test` runs `tests/**/*.test.ts` with [Vitest](https://vitest.dev), in Node, against the engine without a
window or a GPU (`cleo/testing`). A test builds a small world, puts nodes with your scripts in it, plays it for a
while and checks what happened:

```ts
import { describe, it, expect } from 'vitest'
import { createTestWorld } from 'cleo/testing'

describe('Mover', () => {
  it('moves right while Move is held', () => {
    const world = createTestWorld()
    const mover = world.spawn({ name: 'Mover', script: '@/Characters/Mover', vars: { speed: 3 } })
    world.start()
    world.input.setMove(1)   // also press('Jump'), release(…), tap(…)
    world.step(1)            // one second at 60 frames a second
    expect(mover.position[0]).toBeGreaterThan(0)
    world.dispose()
  })
})
```

`script` is the script's path in the Assets panel. Scripts run through the engine's own script compiler, as in the
game, so their imports of other scripts and their decorators behave exactly as they do when you press Play.
`spawn` takes the node's scene JSON for anything else (`type: 'characterBody2D'`, `characterBody2D: { size }`, …).

A test can also play the whole project: `openProject()` loads its main scene (or `scene`) the way a published game
loads it, every model with its animator, every template and script, physics and AI, and steps it tick by tick. A
key press reaches `Input.started` and `@onAction` methods alike. `readProject()` gives the project as data: its
scenes, libraries and Assets tree.

```ts
import { it, expect } from 'vitest'
import { openProject, readProject } from 'cleo/testing'

it('walks the player forward', async () => {
  const game = await openProject()             // or openProject({ scene: 'Level 2' })
  const player = game.find('Player')!
  const start = player.worldPosition[2]
  game.input.setMove(0, 1)
  game.step(2)                                 // two seconds, 60 ticks a second
  expect(player.worldPosition[2]).not.toBe(start)
  game.dispose()
})

it('ships every level', async () => {
  const project = await readProject()
  expect(project.manifest.sceneMetas.map(s => s.name)).toContain('Level 2')
})
```

The engine for `npm test` and the declarations for `npm run typecheck` are in `.cleo/sdk/cleo`, which Cleo writes
when it opens the project; `node_modules/cleo` points at it.

## Projects from before folders

Projects kept in the desktop app's own storage before projects became folders are listed under
**Browser-storage projects** in the project list. They do not open in the desktop app: **Export .zip…** one,
then **Import .zip…** it into a folder.
